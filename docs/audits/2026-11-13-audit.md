## 1. Executive summary

IsolynV2.0 is not scaffolding. It is a working macOS dominoes game with a genuinely well-built C++20 engine, a hardened C-to-Swift boundary, a playable SwiftUI table, and 577 passing automated checks. It builds, it runs, and the packaged app launches.

It is also not a finished product, and several of its most impressive artefacts are less capable than they appear.

The five findings that matter most:

1. **A verified memory-safety defect in a public bridge API.** Recording a 1v1 round into a 2v2 match reads past the end of a two-player hand array. Reproduced 6/6 times: SIGABRT in a debug build, **SIGSEGV in a release build** (`IsolynBridge.cpp:506` → `GameState.cpp:85`). The shipped UI never triggers it because it keeps modes consistent; the API is nevertheless unsafe.
2. **Two of the four entry points on the launch screen do not exist.** Training and Sandbox route to `ComingSoonView`, whose body text is literally "This part of Isolyn hasn't been built yet." (`EntryView.swift:51,54`; `ComingSoonView.swift:10`).
3. **No time control anywhere in the product path.** `SearchEngine::Config::timeLimitMs` defaults to 0 and the bridge never sets it (`SearchEngine.hpp:54`; `IsolynBridge.cpp:622-623`). On the top difficulty tier the UI can sit on "Computer's turn" indefinitely with every control disabled.
4. **The difficulty ladder is mostly cosmetic.** Committed calibration data shows adjacent tiers are statistically indistinguishable, and in two of three adjacent comparisons the *shallower* configuration wins. `docs/subsystems/LAB.md:124` claims "every adjacent comparison favours the deeper configuration"; the repository's own data contradicts it.
5. **One documented rule is unimplemented.** The 1v1 "One Domino Rule" is absent by explicit decision (`MatchController.hpp:29`), so the flagship mode is not fully rules-conformant.

Against those: the bridge's design (handle tables, state versions, typed errors, per-session locking, structural hidden-information isolation) is better than most commercial code of this size, and the test discipline is unusually serious for a single-developer project.

**Overall weighted completion: 57.5% (Grade D).**
Functional completeness 71% · code implementation 72% · validation coverage 52% · production readiness 15%.

The gap between 71% functional and 57.5% overall is not a contradiction: 71% of the *user-facing capability set* exists, but only 57.5% of the *whole engineering programme* — security, performance, persistence, packaging — is done.

## 5. Technical architecture review

### 5.1 What the architecture actually is

```
IsolynApp (SwiftUI, 7,392 LOC, @Observable + MainActor)
  AppState -> RootView -> EntryView / ModeSelectorView / InteractiveGameBoardView / ComingSoonView
  GameViewModel (636) -> EngineSession (actor, 276) -> MatchCoordinator (107)
        |  import IsolynEngineBridge   [.interoperabilityMode(.Cxx)]
        v
IsolynEngineBridge (1,082 LOC, POD-only, uint64 handle tables, per-session mutex,
                    monotonic state versions, typed BridgeStatus)
        v
IsolynEngine (C++20, 3,842 LOC, value-semantic GameState, LIFO undo, zero internal locks)
```

Verified in `Package.swift`: the engine is a library target (`:10`), the bridge is a separate target so only `IsolynBridge.hpp` is visible (`:36`), and the app is an executable target with C++ interop enabled (`:52`, `:63`) that excludes its unused `Info.plist` (`:56`). `cxxLanguageStandard: .cxx20` (`:86`). The test target has the same interop setting (`:82`).

### 5.2 What is strong, with evidence

**The narrow waist is real, not aspirational.** `IsolynBridge.hpp:15` declares a POD-only public surface: every type is an enum, a fixed-size struct of primitives and C arrays, or a `uint64_t` handle. No `std::vector`, `std::string`, pointer, or template crosses the boundary. This is the correct call for Swift/C++ interop stability, and it is honoured throughout 435 lines of header.

**Fail-closed command ordering is implemented, not described.** Every mutating call does version check, then round-state check, then input validation, then legality, then mutate:

```cpp
// bridge_submit_move
if (expectedStateVersion != impl->stateVersion) return failedCommand(BridgeStatus::StaleRequest, ...);
if (impl->cachedRoundOutcome != RoundOutcomeDTO::InProgress) return failedCommand(BridgeStatus::RoundAlreadyOver, ...);
if (!isValidTileDTO(move.tile) || !isValidSide(move.side)) return failedCommand(BridgeStatus::InvalidRequest, ...);
```

`RoundAlreadyOver` was added specifically so a drained tap and a duplicate tap produce different, actionable answers (`IsolynBridge.hpp:138`).

**Hidden information is structural.** `SnapshotDTO` exposes `ownHand[]` and `otherHandSizes[]` only. `finalRevealedTiles[]` and `finalHandValues[]` are populated only when the round has actually ended. The UI cannot leak an opponent's tiles because it never receives them. This is the best architectural decision in the project.

**Engine value semantics and undo are correct.** `GameState::playTile` returns `PlacementKind` so `undoPlayTile` can invert exactly; `undoDrawTile` deliberately searches the hand rather than assuming `back()`, with the regression that motivated it documented in the header. LIFO undo is enforced by preconditions on both the chain and the hand.

**Score: 70/100 (Grade C).**

### 6.2 What the engine genuinely supports

**Search** (`SearchEngine.cpp`, 609 LOC). Iterative deepening to `maxDepthPlies` (`SearchEngine.hpp:48`); per-depth loop over `determinizationCount` sampled worlds (`:49`); alpha-beta negamax with transposition table, killer moves and history ordering for 1v1/2v2; a MaxN variant with no pruning for 1v1v1; cooperative cancellation checked every 256 nodes; a 250,000-entry TT (`SearchEngine.cpp:25`) cleared wholesale when full (`:353`, `:441`); exact endgame solving when the yard is empty and at most 8 tiles remain (`SearchEngine.hpp:61`).

**Terminal scoring is correct, and the fix is documented.** `kTerminalWinScore = 2000.0` (`SearchEngine.cpp:36`) makes a real Domino win outrank the +1000 one-tile-threat heuristic. Committed data corroborates: 781 of 1,000 games terminate by Domino rather than looping.

**Belief/determinization** (`BeliefState.cpp`, `Determinizer.cpp`, `SimulationEngine.cpp`). The constructor allocates each unseen tile across locations proportional to hand size; `Determinizer::sample` samples **without replacement** by weighted choice, re-normalising after each pick; `SimulationEngine::sampleDeterminizedState` preserves the believer's hand, the chain, and play history exactly, and copies the revealed locked boneyard pair rather than resampling it. Tested explicitly, including "the boneyard's already-revealed locked pair is copied exactly, never re-sampled".

**Probability API.** `probabilityHoldsAtLeast` is an exact Poisson-binomial dynamic program over approximated marginals (`ProbabilityEngine.cpp`). The independence approximation is documented and recommended for acceptance in `docs/history/roadmaps/audit-remediation-roadmap.md` Phase 5.

**Entropy.** OS CSPRNG only — `SecRandomCopyBytes` on macOS, `getrandom` on Linux, `BCryptGenRandom` on Windows, each with failure handling and rejection sampling in `uniformIndexBelow` (`EntropySource.cpp`).

## 7. Backend assessment

**Score: 64/100.**

### 7.1 Design strengths

- Integer handles with monotonic IDs and idempotent close (`HandleTable`), avoiding ABA and use-after-free on double-close.
- Per-session `std::mutex`; documented single lock ordering session→match; verified under millions of concurrent snapshot queries during a live analysis (2.16M–6.69M across runs; count varies with scheduling).
- Two-phase analysis: cheap snapshot on the serial context, expensive search on a detached task, cancellation through `std::atomic<bool>`.
- Typed failure taxonomy covering staleness, legality, turn order, empty boneyard, engine exception, and terminal round.
- Match recording is idempotent per session and rejects in-progress rounds.

### 7.2 CRITICAL — verified out-of-bounds read and release segfault

`bridge_match_record_round` never checks that the session's mode matches the match's mode.

```cpp
            for (const auto& tile : state.hand(p)) ...   // p == 3 on a 2-player state
```

`GameState::hand` guards only with an assert:

```cpp
// GameState.cpp:85
const std::vector<DominoTile>& GameState::hand(int playerIndex) const {
    assert(playerIndex >= 0 && playerIndex < playerCount());
```

**Reproduction.** A standalone harness deals a 1v1 session, plays it to completion, then records it into a 2v2 match:

| Build | Result | Exit code |
|---|---|---|
| Debug (asserts live) | `Assertion failed: (playerIndex >= 0 && playerIndex < playerCount()), function hand, file GameState.cpp, line 85` | **134 (SIGABRT)** ×3/3 |

**Impact.** A public API can be driven into an out-of-bounds read by a caller that violates an unstated precondition — exactly the failure mode `IsolynBridge.hpp` rule 4 claims to have designed out. **Fix.** One guard before the branch: `if (state.mode() != m->mode) return failedMatch(BridgeStatus::InvalidRequest);`, plus a regression check in `SmokeTest.cpp`.

### 8.2 Findings

**The state machine is well designed.** `GameViewModel` projects a single snapshot into `loading → playing → roundOver → matchOver`, auto-resolves forced draws with a bounded recursion (`:150`, `:187-188`, `forcedDrawAttempts < 32`), heals stale requests by silent refresh, and records each round exactly once via `recordedSessions` keyed by object identity (`:372`). The AI turn loop is bounded at 64 iterations (`:550`) and falls back to a genuinely legal random move when `samplesCompleted == 0` (`:601`) — the documented honesty contract is actually implemented.

**Accessibility is nominal.** Across 7,392 LOC of SwiftUI there are **11 `accessibilityLabel` sites** and **zero `keyboardShortcut`s**. There is no Dynamic Type strategy: `IsolynTheme.display(_:)` and `.body(_:)` take fixed point sizes. A blind player cannot navigate the game; a player who cannot use a mouse cannot play it.

**No time control makes the top difficulty tier a potential hang.** `AILevel.elite` maps to depth 8 / 64 determinizations (`DifficultyModel.hpp:47-55`), passed straight to analysis (`GameViewModel.swift:545`) with `aiThinking = true` disabling every control and no deadline in the engine (E7).

**Human analysis is hardcoded to a different tier than the opponent.** `GameViewModel` requests depth 4 / 20 determinizations regardless of the selected strength (`:453-454`), so asking for help always gets "Expert" even on Casual, and even versus Elite.

**Two advertised journeys end in a placeholder.** `EntryView.swift:51,54` set `.comingSoon("Training"/"Sandbox")`; `ComingSoonView.swift:10` renders "This part of Isolyn hasn't been built yet."

**Visual verification status:** the app was launched (process alive, then terminated) but not interacted with or visually inspected. All statements about layout quality, motion, and usability are static-analysis or unit-test inferences, not observations.

## 12. Performance and scalability assessment

**Score: 42/100.**

### 12.1 Measured

| Measurement | Value | Source |
|---|---|---|
| Concurrent snapshot queries during one analysis | **2,155,721 – 6,686,634** across runs | `SmokeTest` output |
| Accelerator, 65,536 positions | CPU 1.65–1.70e7/s → Metal **1.84–2.13e8/s** (~10–12×) | `./Accelerator/build.sh` ×2 |
| Accelerator, 1,024 positions | 1.66e7/s → 5.09e6/s (**GPU slower**) | same |
| Host encoding | ~2.65e7 positions/s | same |
| Soak memory | flat, within threshold | `SoakTest` (1 check) |

### 12.2 Structural issues

1. **Search is single-threaded.** The determinization loop is embarrassingly parallel and runs serially. On an 8-core machine this leaves roughly 7× unclaimed before touching the GPU.
2. **Deep copies per candidate per sample.** `GameState trial = world;` inside the candidate loop, then apply, then undo — two copies × candidates × samples × depth.
3. **Transposition table keyed by play history.** `GameState::hash()` mixes every `PlayRecord`, so transpositions that differ only in move order hash differently — the exact case a TT exists for. Hit rate is structurally low.
4. **TT cleared wholesale at 250k entries** (`SearchEngine.cpp:353, 441`) rather than replaced generationally.
5. **No parallelism at the boundary:** a snapshot during a long mutation queues on the session mutex.
6. **Accelerator crossover is ~4,000 positions.** Below that the GPU loses, which is why batched leaves (not per-position calls) would be required.

**Scalability verdict:** the state space is hard-capped at 28 tiles, so there is no data-scale risk. The wall is time-to-move on the top tier, and every mitigation — parallelism, GPU batching, time management — is designed but unwired.

## 15. Implemented strengths

1. **The bridge is genuinely hardened, not performatively hardened.** Monotonic handle IDs, idempotent close, typed statuses, optimistic state versions, fail-closed ordering, per-session mutex, documented lock ordering. Verified under millions of concurrent queries. This is production-grade boundary engineering and the project's best asset.
2. **Hidden information is an architectural property, not a UI convention.** The snapshot physically cannot carry an opponent's tile identities mid-round.
3. **The engine is small, value-semantic and correct where it counts.** 3,842 LOC including headers. LIFO undo with `PlacementKind`; order-independent `undoDrawTile` with the reproduced bug documented; `excludedTilesForMode` shared by dealer and belief construction so the 0-0 rule cannot diverge.
4. **Belief sampling is statistically sound.** Weighted draws without replacement, capacity-exact, preserving everything the believer actually knows — and tested for exactly that.
5. **Test volume and honesty.** 429 + 73 + 75 checks, sanitizer-clean across 21 executables, a real fuzz harness with a documented fallback, and a soak test that measures Darwin RSS instead of silently passing.
6. **Documentation culture.** ADRs, four roadmaps, a fix log with reproduction receipts, and explicit "open question" annotations at the exact lines where the rules are ambiguous.
7. **Zero external dependencies in the app.** SwiftUI plus the C++ engine. Supply-chain risk effectively nil.
8. **Real calibration infrastructure.** The self-play harness links the actual engine, emits 44-column per-move CSVs, and the Python lab produces Elo with Wilson intervals and Spearman correlations. The data is real even where the interpretation overreaches.

## 20. Critical priorities and recommended actions

1. **Fix AUD-01 immediately.** One guard plus a regression test. It is the only demonstrated memory-safety defect, and it sits in the component the project most prides itself on.
2. **Add a time budget to every search the app can trigger.** Without it, "Elite" is not a difficulty setting; it is a hang.
3. **Stop quoting the ladder as monotonic.** Either regenerate the three tier files at adequate sample size or rewrite `docs/subsystems/LAB.md:118-130` to state what the data shows. The project's credibility rests on claims being reproducible.
4. **Decide the difficulty question honestly.** Five tiers spanning about 53 Elo should become three tiers labelled by behaviour, not five numbered 100–3000.
5. **Decide Metal: integrate or archive.** 1,548 LOC and 537 lines of tests that no user can benefit from is the largest deceptively mature artefact in the repository.
6. **Do not start Training or Sandbox before `PositionConstructor` and `ExplanationEngine` exist.** Both documents already say this; the entry screen currently contradicts them.
7. **Repair the vacuous test.** A suite that reports "1 skipped" as if benign is overstating its own coverage by one assertion and one path.
8. **Refresh the inventory and CI labels.** Cheap, and it protects the asset that makes this project auditable.

## 21. Final engineering verdict

**Is this application genuinely functional, or mostly scaffolding?**

Genuinely functional. A 1v1, 1v1v1 or 2v2 match can be dealt, played through forced draws and passes, ended by Domino or Close, scored, and carried across rounds — against a human on one device or a search-driven computer opponent — and the app launches and runs. Two advertised modes, however, are scaffolding.

**How strong is the underlying engineering?**

Strong at the core, weak at the edges. The bridge is the best-engineered part and would not embarrass a commercial codebase. The engine is compact, correct where complete, and well tested. The Swift layer is disciplined about concurrency and error propagation. Packaging, accessibility, persistence, time control and quantitative documentation are those of an unfinished prototype.

**How much of the intended application actually exists?**

71% of the intended user-facing capability set, 72% of the declared module plan, 52% of the validation surface, 15% of the production surface. Overall: **57.5%**.

**How much of what exists is genuinely operational?**

Everything in §13.1 is operational and was executed. The unverified portion is the visual/interaction layer (launched, not driven) and the live-weather path (capability absent, always degrades).

**What are the most serious engineering failures?**

1. A verified release-mode segfault reachable through the public bridge API.
2. No time control anywhere in the product path, making the top difficulty tier a potential hang.
3. A difficulty ladder whose published monotonicity claim is falsified by its own committed data.
4. A rules engine missing a documented 1v1 rule in the flagship mode.
5. A permanently skipping test presented as coverage.

**Which components are deceptively mature-looking but technically incomplete?**

- The Metal accelerator: 1,548 LOC, parity-tested, ~10× CPU, incapable of affecting a move.
- The calibration ladder: 27 CSVs and 130k+ rows whose adjacent tiers cannot be distinguished.
- The DifficultyModel: five tiers, roughly two effective.
- The environment system: 816 LOC of polished time/weather, with live weather permanently unavailable.
- The bridge's own header: still claims match state is out of scope while defining the API that owns it.

**What would prevent this application from reaching production?**

Packaging and distribution, persistence, accessibility, time management, and the two missing modes. None is architecturally hard; all are unstarted.

**What needs rebuilding rather than patching?**

Nothing in the engine or bridge needs a rewrite. Three things need replacement rather than patching: the difficulty-tier mapping (patch it and five indistinguishable tiers remain), the documentation's quantitative layer (regenerate rather than hand-edit — the drift is systemic), and the packaging path (`run.sh` is a development convenience, not a distribution mechanism).

**What is the realistic overall completion percentage?**

**57.5%** overall; 71% of user-facing function; 52% validated; 15% production-ready.

**How much engineering work remains?**

Roughly 40% of the total programme: a day of correctness work, two to three weeks of engine work (parallelism, 1v1v1 search, calibration, Metal decision), the greenfield build of PositionConstructor, ExplanationEngine, Training and Sandbox, a persistence layer, an accessibility pass, and full release engineering. The hard, correctness-critical work is largely done; what remains is breadth, integration and polish.

**One sentence:** the engine and the bridge are better than the product around them, and the documentation is better than the numbers inside it.

## 23. Plain-English summary

Isolyn is a **real, working dominoes game** — not a mock-up. You can deal, play against a friend or the computer, finish rounds, keep score across a match, and see it on a proper table with tiles and animation. It builds, it runs, and its tests pass.

It is also **not a finished product**. Two of the four things the opening screen offers — Training and Sandbox — open onto a sign saying "not built yet." You cannot save a game in progress. You cannot install it on someone else's Mac. And one part of the code that joins the game's brain to its screen can crash if handed the wrong kind of match.

If this were a house: the foundations, plumbing and wiring are genuinely well done. The kitchen and one bedroom are finished and livable. Two bedrooms are framed but empty. There is no front door and no roof certificate, and one loose floorboard will break an ankle if stepped on exactly right.

**About 57% complete. Grade D** — deliberately strict, because the grading measures a shippable product, not effort.

The five different numbers people mix up:

| Question | Answer |
|---|---|
| How much of the code is written? | ~72% |
| How much of the game works for a player? | ~71% |
| How much of it is actually checked? | ~52% |
| How close to handing it to a stranger? | ~15% |
| Overall | **57.5%** |

A car can be 70% built — engine, wheels, seats — and still be 15% ready to sell, because it has no doors, no paint and no paperwork. That is this project.

**Best parts:** the translator layer between brain and screen is professional-grade; cheating is structurally impossible because the screen is never given the opponent's tiles; the brain is small, correct where complete, and honestly documented.

**Worst parts:** the crash; an opponent with no clock; a difficulty dial that is mostly decoration; two advertised modes that do not exist; no saving; no accessibility; nothing shippable.

**What to do first:** fix the crash, give the AI a clock, settle the missing rule, correct the false calibration claim, replace the fake test. Then parallelise the search, decide what to do with the graphics-card work, and only then build Training and Sandbox on top of the two engines they actually need.

**One sentence:** *the game's brain and its translator are better than the product wrapped around them, and the documentation is better than the numbers inside it.*
