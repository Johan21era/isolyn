## 2. Findings that matter

### CRITICAL — mode-mismatched round recording crashed the process

`bridge_match_record_round` indexed hands by the match's mode without checking
the finished session's mode (`IsolynBridge.cpp:486-547`). A 1v1 session recorded
into a 2v2 match reached `GameState::hand(2)`/`hand(3)` on a two-player state;
`hand()` is guarded only by `assert` (`GameState.cpp:84-86`).

Reproduced on `347a5b8`: Debug **SIGABRT (134)**, Release **SIGSEGV (139)**.
Already documented as a known gap in `BRIDGE_ARCHITECTURE.md:124-131`. Fixed in
`e56676e` with `BridgeStatus::ModeMismatch` and a regression in `SmokeTest.cpp`
that also proves the match remains usable.

### HIGH — 1v1 played to 101, not the rulebook's 151

`RulesEngine.hpp:102` hard-coded `kOneVsOneMatchLossThreshold = 101`;
`RulesEngine.cpp:130` used it. `RULEBOOK.md:64` says the default is 151, with 101
only as a pre-game agreement, and its own gap text claimed all modes were locked
at 151. `RulesEngineTests.cpp:135-137` and `ScoreSystemTests.cpp:27-29` enshrined
101. Phase 1 corrected the constant and both assertions; the pre-game 101 option
remains an open R-06 gap.

### HIGH — no wall-clock budget in the product search path

`SearchEngine::Config::timeLimitMs` existed and the engine honoured it
(`SearchEngine.cpp:629-630`), but `bridge_analysis_run` took no time parameter
(`IsolynBridge.cpp:607`) and `GameViewModel` passed fixed depth/sample counts
(`GameViewModel.swift:445-446`, `588-589`). A deep request had no upper latency
bound. Phase 1 added `bridge_analysis_run_with_budget`, 1.5 s for coach analysis
and 3 s for AI, plus a bridge test that asserts truncation is reported.

### HIGH — six declared rule gaps

`RULEBOOK.md:64-100` declares R-06 (101 option), R-07 (sets/games), R-15
(unlimited draws in analysis), R-17 (private locked-pair look), R-18 (One Domino
Rule) and R-22 (1v1v1 elimination). The game is therefore not fully
rules-conformant in any mode.

### HIGH — accelerator is red and unwired

`./Accelerator/build.sh` exited 1 with **94 pass / 6 fail**: four compact-GPU
parity checks, the closed-position parity check, and the multi-mode parity check.
The shader hard-codes `0.25 * teamSupport` (`EvaluationShaderSource.hpp:196,207`)
while the engine uses `teamSupport = 24.0` (`EvaluationEngine.hpp:62`). It has no
references from `Package.swift` or `Sources`, so it cannot influence moves.

### HIGH — numeric documentation drift

`README.md:43-44` said 429 engine / 73 bridge; the tree produced 451 / 74.
`docs/README.md:80-84` mixed a current engine count with Swift 75 (1 skipped),
sanitizer 502 and accelerator 100. `PROJECT_INVENTORY.md` understated the app by
9 files / 2,659 lines. `LAB.md` presented a 4,000-game ladder as separable while
its data is gitignored and the rulebook change had voided every old figure.

### HIGH — locked pair revealed to both players and the AI

`IsolynBridge.cpp:299-303` copied `Boneyard::lockedTiles()` into the snapshot
once the draw pile emptied; `ProbabilityEngine.cpp:13-15` added the same pair to
`otherKnown`, telling the search exactly which tiles could never be drawn.
Contradicts R-17. Phase 1 removed both: the DTO fields are always empty and the
pair remains part of the boneyard's uncertainty.

### MEDIUM — production surface and accessibility

No rules/help/onboarding, pause/menu, undo control, save/resume, match history,
Training or Sandbox. 13 `accessibilityLabel` uses, four keyboard shortcuts (three
in Lab), no Dynamic Type, no keyboard-only way to play a tile, no board semantics
for VoiceOver, no localisation.

### MEDIUM — no production packaging

No app target, `.entitlements`, `PrivacyInfo.xcprivacy`, notarisation, crash
reporting or release process. `run.sh` performs ad-hoc `codesign --force --deep`
and stages the Lab runtime into Application Support. The Lab itself spawns
`/bin/bash scripts/lab` from the app, which is neither sandboxable nor shippable.

### MEDIUM — test infrastructure limits

No coverage measurement, no UI interaction tests (three offscreen Lab renders
only), and the accelerator is red. GitHub Actions runs fail in ~3 seconds with
zero steps; the annotation is an account-billing message, not a code failure.
Local suites are the only executed evidence.

## 4. What the repository genuinely supports

- Three modes (1v1, 1v1v1, 2v2), opening ritual, forced draw, voluntary draw,
  passing, round-end detection, scoring, match accumulation and next starter.
- Legal move generation/validation/execution, exact undo, deterministic deals.
- Belief sampling and determinised parallel search with cancellation.
- A POD C ABI with handle validation, typed errors and state versions.
- A playable SwiftUI table with hand interaction, hover-chain inspection,
  round-end summary and cosmetic settings.
- Strong native test discipline and clean ASan/UBSan/TSan/fuzz runs.

## 5. What is missing or not production-ready

Sets/games, the One Domino Rule, 1v1v1 elimination, the 101 option, the private
locked-pair look, unlimited analysis draws, Training, Sandbox, rules/help,
pause/menu/undo, save/resume/history, accessibility, localisation, packaging,
signing, notarisation, privacy manifest, crash reporting, coverage, UI tests and
a working hosted CI. See `docs/audits/2026-11-13-audit.md` §15 for the detailed
inventory; it remains accurate except where superseded above.

## 6. Priority order

1. Finish rule conformance: R-06 option, R-07, R-18, R-22, R-15, R-17 look.
2. Re-measure the difficulty ladder and strength under the current rules; publish
   only in `docs/research/STRENGTH_BASELINE.md`.
3. Product surface: rules/help, pause/menu/undo, save/resume/history.
4. Training and Sandbox, or remove the promise.
5. Accessibility, localisation.
6. Accelerator: restore parity and wire it, or archive it.
7. Packaging, privacy, notarisation, crash reporting.
8. CI billing and required suites; coverage and UI tests.

## 7. Verdict

The engine and bridge are real, tested and worth preserving. The product around
them is about half finished and cannot ship: no packaging, no accessibility, no
persistence, no rules/help, and six declared rule gaps. The most serious defect
found by this audit (the mode-mismatch crash) has been fixed; the next most
serious is the still-unimplemented rules surface. **52.6% weighted, Grade D.**
